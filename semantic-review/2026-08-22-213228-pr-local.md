# N1MM+ discovery relay, forward direction/dedup, serial bridge wizard

This change adds three capabilities: (1) an N1MM+ discovery broadcast relay that captures N1MM inter-station announcements on the Station and re-emits them on the Client's LAN, (2) a `Direction` field on forward rules enabling Station-to-Client (reverse) traffic flow with deduplication logic on the Station, and (3) a serial bridge wizard path that generates VSPE configuration files for CAT-over-TCP bridges. The UI is reorganized into a 3-tab layout (Keyer, Ham Router, Log) separating keying concerns from port forwarding. Watch for: the N1MM emitter is never disposed on the Client (confirmed), the `_activeForwards` dedup set is never pruned when a rule is disabled mid-session (confirmed), and the `StationController.Dispose()` path does not stop the N1MM listener if a session is still active (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The N1MM relay mirrors the existing FlexRadio VITA-49 discovery pattern: a Station listener captures UDP broadcasts and forwards them base64-encoded over the control channel; the Client emitter rewrites the IP and re-broadcasts locally. The lifecycle is gated by session start/end and the config flag, but disposal at controller teardown is incomplete — both the Client emitter and the Station listener can survive a `Dispose()` call if a session is active.

The forward direction model adds `ForwardDirection.StationToClient` as a first-class concept. The Station's rule processor now branches on direction before calling into the sidecar host. Deduplication prevents redundant sidecar registrations when the Client resends its rule list, but there's no mechanism to remove entries from the dedup set when a rule is later disabled — the set only clears on session end.

The dedup conflict check for inbound forwards guards against same-port/different-target collisions. The reverse-direction branch skips this check entirely, relying on `clientPort` uniqueness — fine in practice but asymmetric, and two reverse rules targeting the same `clientPort` with different intents would silently dedup incorrectly.

`StationConfig.AllowN1mmRelay` defaults to `true`, meaning existing Stations will start the N1MM UDP listener on upgrade even if the user hasn't opted in. The listener is passive (only forwards to connected Clients, and the Client ignores packets unless enabled), but operators auditing their network listeners will see a new port 2237 bind.

## N1MM relay lifecycle gaps

`ClientController.Dispose()` (line ~1297) does not touch `_n1mmDiscoveryEmitter` or `_discoveryEmitter`. Both hold a `UdpClient` socket. The N1MM emitter's `Dispose()` implementation properly cleans up the socket, but it's never called:

```csharp
// ClientController.Dispose() — no emitter cleanup
_tailscaleNode.Dispose();
_failureHandler.Dispose();
_portForwardManager.Dispose();
_sidetone.Dispose();
_keyer.Dispose();
_hardwareWinKeyerHost?.Dispose();
_winKeyerHost.Dispose();
_paddlePoller.Dispose();
// _discoveryEmitter?.Dispose();   ← missing
// _n1mmDiscoveryEmitter?.Dispose(); ← missing
```

On the Station side, `StopN1mmListenerInternal()` correctly disposes the listener and is called on session end. But `StationController.Dispose()` doesn't invoke it. If the Station process is shutting down while a session is still technically active (the session-end event hasn't fired yet), the listener's socket and receive-loop task persist until GC finalizes them.

## Forward dedup: grow-only set within a session

The `_activeForwards` HashSet is cleared on session end, which prevents cross-session pollution. Within a session, entries are only ever added:

```csharp
lock (_activeForwards) { alreadyRegistered = !_activeForwards.Add(key); }
```

The Client resends its full rule list on every change (toggle a rule on/off in the UI triggers `SendForwardRulesToStation`). If a rule is toggled off, the Station doesn't register a new forward — but the old entry stays in `_activeForwards`. If it's later re-enabled pointing at a different target (e.g. user edited the rule), the conflict check rejects it:

```csharp
if (existing.Kind == key.Kind && existing.TailnetPort == port && existing.Target != targetAddress)
{
    conflict = true;
    break;
}
```

The fix is to compute the desired set of active forwards from the incoming enabled rules, remove stale entries, and only register net-new ones. Alternatively, clear the set and re-register everything on each message (acceptable if sidecar `CreateInbound*` calls are idempotent).

## Reverse-direction dedup key uses nullable session address

For `StationToClient` forwards, the dedup key is:

```csharp
var key = ("out-" + protocol, clientPort, _sessionManager!.CurrentSession?.ClientAddress ?? "");
```

`CurrentSession` should always be non-null inside `ProcessControlMessageAsync` (since it's only called while a session is active), but the `?.` operator plus empty-string fallback means a defensive null check masks a logic error silently. If `ClientAddress` were ever null, all reverse-direction rules would share target `""` and only the first would register — the rest would dedup as "already registered". Using `!` (or an explicit guard that logs a diagnostic and returns) would surface the bug instead of hiding it.
